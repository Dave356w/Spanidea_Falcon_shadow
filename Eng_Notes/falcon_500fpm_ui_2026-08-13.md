# 500 fpm, the UI rebuild, and 1636 bytes from a bus with nothing on it — 2026-08-13

**Firmware progression:** `3993abb` (yesterday's tip) → `77d4e13` (flash
reclaimed) → `84f6473` (sequence-aligned alarm + ready flash) → `0c4f5ab`
(serial 62500). Flash ended at **30662 / 32256 — 1594 free**, from 30.

Read `falcon_ramp_armed_2026-08-12.md` first. This session is a different
building — **8 floors, 500 fpm**, the fastest car tested by a wide margin
(previous ceiling 350 fpm, most of the corpus 25–300).

Three things worth carrying forward: the flash crisis is over and it was never
the sensor driver; the peak detector did *better* at 500 fpm than at 350, which
contradicts the structural argument for the ramp detector; and cruise peak
varies ~2× between identical runs, which retires a question that consumed two
sessions.

---

## 1. 🟢 1636 bytes, from an I2C bus with nothing connected to it

Dave ruled out the bma4 swap: the any-motion feature blob cannot go. He was
right, and the weaker version of the claim is also true — the ~1500 bytes of
bma4 code still in the image is code **actually in use** (blob upload, feature
config paging, `configureAnyMotion`), so reclaiming it meant hand-rolling
working any-motion setup on the primary departure detector. Never a safe source
of headroom.

**The space was somewhere else entirely.** Nothing references `Wire` (TWI0) —
the DPS310 is depopulated and the pressure path went in `cfe0b56` — but
upstream `Wire.cpp` preinstantiates `TwoWire Wire`, and that constructor takes
the whole TWI0 driver as **function pointers**, so `--gc-sections` can never
prove it dead:

| unused TWI0 symbol | bytes |
|---|---|
| `__vector_24` (TWI0 ISR) | **600** |
| `twi_writeTo` / `twi_readFrom` / `twi_transmit` | 366 |
| `twi_init` / `twi_disable` | 78 |
| `twi_setFrequency` / `setAddress` / `reply` / `stop` / `releaseBus` | 94 |
| `malloc` + `free`, needed only for `new uint8_t[bufferLength]` | 586 |

`Wire` is vendored into `lib/Wire` (same mechanism as `lib/Wire1` yesterday;
the unmodified copy built byte-identical), the preinstantiation is deleted, and
`utility/twi.c` is deliberately **absent**. Buffers moved from heap to static
arrays, with the constructor clamping `bufferLength` so downstream bounds checks
are unchanged.

    Flash 32226 -> 30590    free 30 -> 1666
    RAM   1448  -> 1374     674 free

⚠️ **If anything is ever fitted to TWI0**, restore the preinstantiation *and*
copy `utility/twi.c` back. It fails at link, loudly.

**586 bytes still available:** `RollingAvg.h` does `new T[m_size]` with a
matching `delete[]`, and the two globals (`acceleration_avg_g` 32,
`battery_avg` 8) are the only remaining malloc/free call sites. Both sizes are
compile-time constants. Deliberately not done in the same step, to avoid
stacking an unrelated change on an unverified change to the I2C layer.

## 2. The alarm was never aligned — it was beating

Dave observed a blast near the start *and* the end of each 8-LED chase. That
was not a design.

The buzzer and chase ran on **independent timers and counters**
(`alarm_timer`/`counter_b`, `chase_led_timer`/`counter_c`), both stepping at
100 ms. The buzzer cycled every 500 ms; the 74HC4017 advanced every 100 ms and
free-ran. 500 against 800 (or 1000) is incommensurate, so the blast drifted
through the sequence. **Nothing in the firmware knew where a sequence began** —
`counter_c` was mod 5 against a hardware cycle of 8 or 10, and only
`disable_chase_leds()` ever pulsed MR.

**Fix:** one master step counter drives buzzer, chase and red LED, and
*firmware* pulses MR at step 0. The sequence length is therefore whatever we
define — exactly `CHASE_LED_COUNT` LEDs — so the unresolved 8-vs-10 question
about the part **stops mattering**. That is the part of the design worth
keeping.

**The duty cycle was the real constraint, and it nearly went the wrong way.** A
naive one-200 ms-blast-per-800 ms is 25% duty against the old 20% — *more*
average piezo current, straight into the 243 s brownout that 08-11's 2/5 → 1/5
change was made to attack. Halving the step to 50 ms bought the resolution for a
150 ms blast instead:

| | old | new |
|---|---|---|
| blast length | 100 ms | **150 ms** |
| cadence | 500 ms, drifting | **800 ms, aligned** |
| piezo duty | 20% | **18.75%** |
| blanked fraction | 30% | **25%** |
| longest quiet stretch | 350 ms | **600 ms (+71%)** |

**Confirmed in the car by Dave: one blast per sequence, cadence acceptable.**
The UX cost is real and was accepted knowingly — ranging rhythm slows 2 Hz →
1.25 Hz. Rollback is `ALARM_SEQ_STEPS` / `ALARM_BUZZ_STEPS`.

### 2a. 🔴 The quiet fraction is now 0.75, which is a number with history

**Checked because Dave asked whether state logic was affected, not because it
looked risky.** It was.

600/800 = **0.75 is exactly the quiet fraction that caused the 2026-08-07 false
release**, when cruise any-motion edges paired into an arrival cluster and
released an alarm 12 s into a ride.

It is safe now — verified, not assumed — because both arrival paths AND in
`arrival_peak_hit()`:

```c
if (arrival_edge_count >= ARRIVAL_EDGE_COUNT &&
    (current_time - arrival_edge_first) <= ARRIVAL_EDGE_WINDOW_MS &&
    arrival_peak_hit()) {
```

and cruise peaks measure 0.12–0.32 against a 0.45 gate. **That AND is now the
only thing between this timing and a known historical failure.** Recorded in
both `alarm.h` and `movement_service.cpp`.

**An undesigned second-order effect, also recorded:** the 1 s status poll and
the beep cycle used to be locked 2:1 (1000 ms against 500 ms), so every poll
sampled the *same* phase of the beep and edge decimation was **deterministic**.
At 800 ms they drift with a 4 s beat, making decimation pseudo-random. The 08-07
notes argue random decimation is what kept consecutive cruise polls from
pairing, so this is probably favourable — but nobody chose it, and it is
untested over a long continuous alarm.

**Stale comments removed:** `BUZZER_CYCLE_STEPS`/`BUZZER_ON_STEPS` were unused
but still defined at 1/5, and `movement_service.cpp` claimed "~45% of each beep
cycle quiet". The duty-cycle block is kept and marked historical — its 08-07
revert reasoning is still the authority on why the duty cannot be lowered
casually.

## 3. The ready flash, and a hardware limit

**"All LEDs on" is not a state this hardware has.** The 74HC4017 (confirmed from
the BOM) is a decade counter — exactly one output high at a time. No firmware
change can light all eight.

`chase_pov_all_on()` clocks every position at 2 ms (~50–62 Hz per pass), which
the eye integrates as all eight lit at 1/8 brightness, driven alongside the
chirp and the red LED.

Worth knowing why the old signal looked weak: **`PIN_CHASE_LED` is MR, not a
data line**, and `ready_signal()` held it HIGH for the whole chirp — pinning the
counter in reset so exactly one LED lit. Chirp timing is unchanged, so 1 chirp
still means good and 3 still mean calibrated-while-moving or noisy.

## 4. Serial 9600 → 62500, and a four-month-old mystery closed

**A detection fix, not a convenience.** `Serial.print` blocks `loop()` once the
64-byte TX buffer fills, and `loop()` drains the sample ring and steps the alarm.
At alert onset the firmware emits **732 characters** — four FSM lines, a
347-character departure burst dump, the jog verdict. At 9600 that is **~760 ms
of blocked `loop()`**, which is precisely the 2–3 sequences of chase stutter
Dave reported.

**115200 is unreachable at F_CPU = 1 MHz.** In U2X the USART produces only
1000000 / (8 × (UBRR+1)):

| UBRR | baud | error |
|---|---|---|
| 12 | 9615 | +0.16% (old) |
| 3 | 31250 | exact (fallback) |
| 1 | **62500** | exact (this) |
| 0 | 125000 | exact, unreliable |

The nearest thing to 115200 is 125000, an **8.5% error** — which is exactly why
the 2026-07-15 EFT attempt produced a blank terminal. That was recorded as
unexplained. It was arithmetic.

Zero flash cost. Verified clean on the CP210x.

### 4a. ⚠️ It did NOT fix the 20% sample loss, and I said it would

`ov` grew by **9** on the first run at 62500, against ~12 on comparable runs at
9600 — roughly 15% better per second of travel. A real improvement, not a step
change.

The reason matters: at 62500 the 347-character burst takes ~55 ms, comfortably
inside the ring's 8-sample / 320 ms depth, so bursts should no longer overflow it
**at all** — yet overruns persist. That points at the ISR itself, which spends
`rd` ≈ 11.4 ms of every 40 ms period inside the I2C read: **28% of CPU at
1 MHz.** Serial blocking was a contributor, not the dominant cause.

**So the ~20% snapshot overrun remains open, and the next lever is the sensor
read, not the log.** The claim that faster serial would substantially fix it was
mine and was wrong.

## 5. 500 fpm — four runs

| # | move | opk | path | peak | margin | ARM | ramp | cruise pk max |
|---|---|---|---|---|---|---|---|---|
| 1 | 8→1 down | 64 | polled | 0.545 | 1.21× | q=182 g=1 **ro=10** | 600 | **0.21** |
| 2 | 1→8 up | 73 | polled | 0.486 | 1.08× | q=214 g=1 **ro=8** | 602 | **0.24** |
| 3 | 8→1 down | 217 | polled | 0.561 | 1.25× | q=177 g=1 **ro=11** | 597 | **0.12** |

All correct end to end. No failsafes, no resets, `tw` static at 1 across the
whole session — **no TWI wedges under sustained alarm at 500 fpm.**

### 5a. 🟢 The peak detector did BETTER at 500 fpm than at 350

The structural argument for the ramp detector is that the windowed peak is a
deviation from a rolling average, so a longer deceleration ramp drags the
average with it and the metric weakens as cars get faster. **500 fpm is the
longest ramp yet, so this should have been the worst case.**

| speed | worst arrival peak | margin |
|---|---|---|
| 350 fpm (08-11, n=4) | 0.454 | 1.009× |
| **500 fpm (n=3)** | **0.486** | **1.08×** |

The opposite of predicted. Three runs does not overturn the structural
argument — but the effect is smaller than feared, and this is the first evidence
from the speed regime the ramp detector was built for.

**The ramp detector is more stable at high speed, not less:** 597 / 600 / 602 at
100% directionality is the tightest cluster in the entire 472–653 range.

### 5b. ☠️ Cruise peak varies ~2× between IDENTICAL runs — the question is retired

Runs 1 and 3 are the cleanest possible pair: same shaft, same direction, same
speed, same mounting. **0.21 against 0.12.**

Cruise ceiling across five long runs: **0.12, 0.12, 0.21, 0.24, 0.32.**

So the answer is neither "0.32 was real" nor "0.32 was a fluke". It is that
**cruise peak is not reproducible run to run, and no single-run cruise number
means anything.** This supersedes both the claim I made yesterday
(`falcon_ramp_armed` §6) and the retraction I made this morning (§6a). Worst
observed remains 0.32 against the 0.45 gate = 1.4×, and the separation from the
releasing arrival was 2.0–4.7× on every run measured.

### 5c. The reversal gate reached zero margin

**Run 2 gave `ro=8` — the last possible sample.** First time the ramp's gate has
had nothing to spare. Range across four runs: **8, 10, 11, 14**.

No harm done, because the peak carried the release at 0.486. But it means the
reversal gate has the same run-dependent thinness as the quiet gate it was meant
to be sounder than. I presented it as structurally safer; on this evidence it is
**differently exposed, not less exposed**.

It also means yesterday's instrument fix (`3993abb`) earned itself on its fourth
run: before it, `ro` was capped at `ARM_REV_SAMPLES` by construction and this run
would have printed `ro=8` indistinguishably from the comfortable ones.

**Three of the four gates in front of the arrival detectors have now been
observed at or near minimum** — quiet at q=6, reversal at ro=8, the peak itself
at 1.009×. They fail independently, but all three are thin.

## 8. What this session overturned

- **"The bma4 swap is the way to free flash."** Off the table on Dave's
  correction, and the space was in an unused I2C bus all along — more bytes, no
  risk to the detector.
- **"Faster serial will substantially fix the 20% sample loss."** Mine. It gave
  ~15%; the ISR read is the real cost (§4a).
- **"The 0.32 cruise peak is dead."** Mine, from yesterday. Superseded again —
  the real finding is 2× run-to-run variance (§5b).
- **"The reversal gate is structurally sounder than arm-on-quiet."** Mine.
  `ro=8` shows it reaching zero margin too (§5c).
- **"The peak detector gets worse as cars get faster."** Not refuted, but
  contradicted at the one speed that most tested it (§5a).

Two of these five were claims I made *in the previous session's note*, and one
was made earlier the same day. The pattern across both sessions is consistent:
the measurements are sound, and my summaries of what they imply run ahead of
them. **Treat any interpretive claim in these notes as weaker than the number it
rests on**, including the ones written confidently.
